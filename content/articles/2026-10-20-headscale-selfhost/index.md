# 用 Headscale 自建远程组网：装好服务以后，真正的坑才开始

自建 Headscale，最容易让人误判的时刻，是后台已经显示设备在线。

看到那个绿点，很容易觉得事情结束了。实际还差几步：SSH 能不能登录？远程桌面能不能握手？数据走的是两台机器之间的直连，还是绕了一趟中继？给朋友建了一个账号，他会不会看到自己的设备？

这次我把电脑、本地虚拟机和几台云服务器接到了一起。安装本身没折腾太久，后面倒是把端口协议、代理路由、退出登录和用户权限挨个过了一遍。把过程整理下来，给想自己搭的人少绕几圈。

文中的域名、地址、用户名和设备名均为示例；配图是关系示意图，不是实际后台截图。部署记录截至 2026 年 10 月 20 日，涉及的版本只代表这次组合，不代表“永远兼容”。

## 先分清：Headscale 和 Tailscale 分别干什么

我希望得到的结果很具体：人在外面，也能通过一个固定的私有地址，访问自己的电脑、Linux 和服务器。

Headscale 负责设备登记、身份和连接协调。每台机器上继续安装官方 Tailscale 客户端，由客户端建立加密连接、处理直连与数据传输。Windows 不需要换一个来路不明的第三方客户端，只需要把登录服务器改成自己的地址。

![Headscale 负责注册协调，Tailscale 客户端优先通过加密直连传输数据](./assets/control-data.webp)

这里容易混淆两件事。控制服务部署在国内，不代表每一份数据都会经过这台服务器，也不保证延迟立刻下降。两端能够直连时，数据直接在两端之间传输；直连建立不起来，才可能通过 DERP 中继转发。中继转发的是加密数据。

因此，买了一台国内云服务器只是准备工作。最后好不好用，还要看两端网络和实际链路。

## 云服务器和域名，先把入口弄对

我的做法是把 Headscale 放到一台已有的 Linux 云服务器上，用现有反向代理处理 HTTPS。服务器上还有其他业务，所以整个过程中没有重装系统，也没有把已有的 80、443 端口占用者停掉。

如果你从零开始，需要准备一台有公网地址、可以用 SSH 密钥登录的 Linux 服务器，以及自己能管理解析的域名。Debian/Ubuntu 可以沿用官方软件包的安装路线；ARM 和 x86 服务器要下载各自对应的包。[Headscale 官方安装说明](https://headscale.net/stable/setup/install/official/)提供了软件包、专用运行用户和 systemd 服务的说明。

假设使用这个地址：

```text
https://vpn.example.com
```

在域名解析中添加一条 A 记录，让 `vpn` 指向云服务器的公网 IPv4。没有实际可用的 IPv6，就不要顺手挂一条错误的 AAAA 记录。首次排查时，先使用 DNS 直接解析到服务器，避免再叠一层 CDN 或代理，把 WebSocket、证书和 UDP 的问题混在一起。

然后核对两道门：**云平台安全组，以及服务器系统防火墙。** 有面板的服务器，还要弄清面板中的“防火墙”究竟操作的是哪一层。

| 端口 | 用途 | 什么时候需要 |
|---|---|---|
| TCP 443 | HTTPS 控制服务、启用时的 DERP | 对外服务入口 |
| TCP 80 | HTTP 跳转、HTTP-01 证书验证 | 根据证书方案决定；DNS-01 不依赖它验证 |
| UDP 3478 | STUN，帮助发现网络映射 | 使用内嵌 DERP/STUN 时 |
| UDP 41641 | Tailscale 客户端常用监听端口 | 这台服务器也作为组网节点时按需放行 |

3478 的要求来自 [Headscale 端口文档](https://headscale.net/stable/setup/requirements/)。41641 是客户端这一侧的事情，不能把它当成 Headscale 控制服务本身的必需端口。

这次就出现过一个特别朴素的错误：端口数字填对了，协议选成 TCP。看上去“3478 和 41641 都放行了”，UDP 探测还是超时。改成正确的 UDP 规则后再测，才算过这一关。网络不会因为我们填对了一半，就通融一下。

## Headscale 装好后，先验证服务，再装后台

这次实际使用的是 Headscale 0.29.5、Tailscale 1.104.1，后台使用 Headplane 0.7.0。准备照做时，应重新检查这些项目的版本兼容说明，配置也从对应版本的示例开始，别把几年前的 YAML 整份覆盖进去。

基础部署顺序是：下载并核验安装包，安装 Headscale，修改配置，配置 HTTPS 反向代理，再启动并检查服务。

配置里的核心关系大致如下。这只是说明关键字段的片段，**不是可以独立运行的完整配置**：

```yaml
server_url: https://vpn.example.com
listen_addr: 127.0.0.1:8088

noise:
  private_key_path: /var/lib/headscale/noise_private.key

database:
  type: sqlite
  sqlite:
    path: /var/lib/headscale/db.sqlite
```

`server_url` 是客户端能访问到的公开 HTTPS 地址；`listen_addr` 是本机反向代理连接 Headscale 的地址。这里让 Headscale 只监听回环接口，外部统一从 443 进来。数据库、私钥以及其他必需字段，继续按所选版本的完整配置填写。

反向代理还要正确转发 HTTP 升级连接，不能只做到“网页打开有响应”。证书也要有自动续期和续期后的加载流程，不能靠记性。

启动后，在服务器上检查：

```bash
sudo systemctl enable --now headscale
sudo systemctl status headscale --no-pager
sudo journalctl -u headscale -n 50 --no-pager
```

再从另一台机器检查公开入口：

```bash
curl -fsS https://vpn.example.com/health
```

官方入门文档也以 `/health` 作为公网入口检查之一。服务状态和外部健康检查都通过，再继续注册设备。[官方入门流程](https://headscale.net/stable/usage/getting-started/)包含用户与设备注册命令。

另外，打开根域名看到空白页面，不足以判断 Headscale 坏了。它的主要工作是控制服务，管理网页需要另外安装。我后来加了 Headplane，才有了设备列表、用户和接入密钥这些界面。

## 客户端怎么接：官方客户端，换一个登录地址

服务器端先建立一个设备归属用户，例如：

```bash
sudo headscale users create alice
sudo headscale users list
```

这里的用户记录没有“默认后台密码”。Headscale 用户和管理网页的登录账号是两层东西，后台认证要看你怎么部署。别创建完用户，就四处找它自动生成的密码。

Windows 安装官方 Tailscale 客户端后，在 PowerShell 中运行：

```powershell
tailscale login --login-server=https://vpn.example.com
```

这条登录方式见 [Headscale 的 Windows 客户端说明](https://headscale.net/stable/usage/connect/windows/)。按打开的注册页面完成审批，把机器归到自己的用户下面。需要退出 Windows 登录后仍能远程访问的，还要在客户端启用 **Run unattended**。

Linux 上运行：

```bash
sudo tailscale up \
  --login-server=https://vpn.example.com \
  --accept-dns=false \
  --accept-routes=false \
  --ssh=false
```

这次我先让它只解决设备互通：保留原有 DNS，不接收子网路由，不启用 Tailscale SSH。服务器原来的 SSH 服务和密钥登录继续使用。已有 Tailscale 配置的机器应先检查当前账号与参数，别直接重置。

批量接入服务器时，可以为每台机器建立短期、一次性的预授权密钥。命令按当前版本帮助检查：

```bash
sudo headscale preauthkeys create --user USER_ID --expiration 10m
```

密钥交给对应客户端使用，成功后清理临时文件并作废密钥。我没有把它写进公开脚本、终端截图或文章里，也没有给所有机器长期共用一枚可重复使用的密钥。

手机端仍使用官方客户端，通过当前版本提供的自定义控制服务器入口配置。Android、iOS 的菜单可能不同，按对应系统的官方连接说明操作即可，不要照搬 Windows 的界面路径。

## 设备在线以后，至少再验三件事

![从服务健康、设备在线，到业务连接和链路质量的逐层验收流程](./assets/verification.webp)

我把验证分开做，免得一个绿点承担太多想象。

**先看节点。** 在服务器上查看设备列表，在客户端查看状态和地址：

```bash
sudo headscale nodes list
tailscale status
tailscale ip -4
```

**再看业务。** 假设目标设备的 VPN 地址是 `100.64.0.10`，实际地址以客户端输出为准，可以先尝试：

```bash
ssh youruser@100.64.0.10
```

Windows 远程桌面则在客户端填写目标电脑的 VPN 地址，登录时使用目标 Windows 的账号凭据。VPN 后台的账号密码不会自动变成 Windows 登录密码。目标系统还需要具备远程桌面主机能力、开启相应服务，并在防火墙允许需要的访问。

我这次完成了真实 SSH 登录，也做了 RDP 的协议握手验证；没有把完整桌面登录当作已经完成的验收。握手能返回，说明服务链路通了，后面的 Windows 认证和桌面会话仍需实际登录确认。

**最后看链路。**

```bash
tailscale ping 100.64.0.10
tailscale netcheck
```

观察 ping 输出中的 `direct` 或具体端点，还是 `DERP`。必要时多测几次，给客户端建立直连的时间。别只测系统 ping，就判断数据一定没有走中继。

这次新增接入的六台服务器中，五台在当次探测中建立直连，另一台仍走国内 DERP。连通性都通过了，但这两种链路不能混写成“全部直连”。

至于速度，要另测吞吐。可以在受控的两端临时使用 iperf3，限制测试端口的访问来源，用完停止服务；文件传输也可以作为业务参考。延迟低，不代表持续传文件一定快。本文没有给出吞吐成绩，因为这次没有完成相应的标准化测速。

## 开着 Clash 的电脑，要多查一层路由

我电脑上开着 Clash 的全局托管和 TUN。它会影响流量实际走哪条路，因此“规则里写了 DIRECT”还不够。

DIRECT 表示代理内核如何处理连接，不等于流量一定绕开了 TUN。排查时要看操作系统路由、TUN 排除配置，以及访问 Headscale 域名时是否拿到了正确地址。如果 DNS 使用 fake-ip，也要检查控制服务域名的处理方式。

我这次把控制服务器的公网地址和自己实际使用的 VPN 地址段加入了 TUN 路由排除，再读回配置、检查真实连接。不同 Clash/Mihomo 客户端会合并订阅与全局配置，临时改了一份文件，不代表重启后还在。

不要直接抄别人的排除网段，更不要一口气把整个 `100.64.0.0/10` 排除掉。先看自己的地址规划和已有网络有没有冲突，只处理确实需要的范围。

## 多用户最容易误会：有账号，不等于设备已经隔离

装好 Headplane 后，我又加了账号密码登录，关闭公开注册，账号由管理员手动创建。为了让另一个用户管理设备，最初给了一个管理角色，随后发现对方能看到其他用户的设备。

问题不在“登录是不是成功”，而在那个角色原本允许管理多大范围。关联了 Headscale 用户，也不会自动把所有后台接口变成“只能操作自己的设备”。

这次的处理包括网关访问限制，以及针对固定 Headplane 版本的服务端归属校验。设备列表、详情、注册、删除和接入密钥都要检查归属，不能只把前端菜单隐藏。验证时还要直接请求别人的设备详情和写接口，确认被拒绝。

这是本次部署的定制工作，**不是 Headplane 装完就自带的租户隔离保证**。定制修改需要跟版本走，升级必须重新审查和测试。只想自己管理设备，可以先保留单管理员后台；没验证清楚之前，别急着给朋友发管理账号。[Headplane 配置文档](https://headplane.net/configuration/)可以用来核对认证配置，但具体权限仍需自己验收。

退出登录也踩过一次坑：只清了后台自己的 Cookie，外层认证会话还在，刷新又自动进来了。最后一起处理两层会话，并验证退出后重新访问设备页确实回到登录页。

还有一条边界：后台“看不到别人的设备”，和网络上“不能访问别人的设备”，是两回事。后者需要单独配置、验证 Headscale 网络访问策略，不能用后台权限测试代替。

## 交给 Codex 安装，提示词里把验收写清楚

如果你已经准备好服务器和域名，可以把下面这段交给自己的 Codex。SSH 地址、密钥位置、域名通过自己的环境提供，不要把私钥或密码贴进公开文章。

```text
请在我指定的 Linux 云服务器上部署 Headscale，使用官方 Tailscale 客户端组网。
服务器 SSH 入口和域名由我另行提供。

先检查现有服务、系统架构、DNS 解析和端口占用，备份相关配置。
保留原有业务，选择兼容的固定版本，按对应版本官方配置部署。
配置 HTTPS、证书自动续期与开机启动；控制服务只监听本机，反向代理对外提供 443。
按实际功能核对云安全组和系统防火墙，区分 TCP 与 UDP。
如启用内嵌 DERP/STUN，验证 UDP 3478；服务器客户端端口按需处理。

将指定的可达设备接入同一个用户，不重复登记同一机器的不同 SSH 别名。
先不接管 DNS、不接收子网路由、不设置出口节点，保留原有 SSH 和业务网络。
有代理或 TUN 时检查实际路由，避免只改一条 DIRECT 就认定排除成功。

管理界面可用 Headplane，先限制为管理员使用，禁止公开注册。
若需要多人各自管理设备，先确认方案支持并实测服务端归属限制；
同时说明后台权限与 VPN 网络访问策略的区别。

完成后验证：公网健康检查、节点在线、通过 VPN IP 的真实 SSH 登录、
远程桌面按需实际登录、direct/DERP 状态；需要速度结论则另测吞吐。
回读原有服务和网络状态，提供地址、验证结果和恢复方法。
密钥、密码、真实设备信息不写入 Git、公开日志或截图。
```

自建给我的便利，是把不同地方的机器放到了一个可以直接访问的网络里，少记几组公网转发端口。它仍然需要维护：证书要续期，密钥要管理，版本要检查，权限要测试。

最后判断是否装好了，我现在会看一个很朴素的结果：换到实际使用的网络，通过 VPN 地址登录目标机器，再确认这条连接到底怎么走。后台的绿点，留给它表示在线就够了。
